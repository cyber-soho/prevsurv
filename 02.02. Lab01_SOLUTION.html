0Files in place

Put both lab files in ~/Desktop/lab01/ inside the Parrot VM, then check they are there.

mkdir -p ~/Desktop/lab01# make the lab folder (the -p means 'don't error if it already exists')
cd ~/Desktop/lab01# move into that folder so every later command runs from here
ls# list the folder contents to confirm both files are present
Expected: lab01_auth.log  lab01_sample.pcapng

1Environment setup (one time)

Confirm your tools exist, then allow Wireshark to run without root warnings.

wireshark --version | head -1# print Wireshark's version (head -1 = just the first line)
tshark --version | head -1# tshark is Wireshark's command-line twin; check it too
which awk grep sha256sum# show the file paths of the three tools we'll use for analysis
sudo dpkg-reconfigure wireshark-common# re-run Wireshark's setup; choose <Yes> when asked about non-root capture
sudo usermod -a -G wireshark $USER# add yourself to the 'wireshark' group ($USER = your username)

Set network isolation in VirtualBox → VM → Settings → Network → Adapter 1 → Host-only Adapter (or untick Enable Network Adapter). Screenshot that panel for your report.

2Open the capture and read the protocol map

In the terminal, get a text summary first, then launch the graphical Wireshark on the same file.

cd ~/Desktop/lab01# make sure you're in the lab folder
tshark -r lab01_sample.pcapng -q -z io,phs# -r = read file, -q = quiet, -z io,phs = show the Protocol Hierarchy summary
wireshark lab01_sample.pcapng &# open the file in the Wireshark GUI; the & lets you keep using the terminal

In the Wireshark GUI: click Statistics → Protocol Hierarchy. The window lists every protocol in the capture. This is your map — it shows DNS, HTTP and SSH, so those are the three things to investigate.

Close the Protocol Hierarchy window when done.

3Find the malicious download

In the Wireshark GUI: click Statistics → Conversations. Click the TCP tab, then click the Bytes column header to sort biggest-first. The chattiest external host is 203.0.113.45. Select its top row, then click Follow Stream…

A Follow HTTP Stream window opens. Red is what your workstation sent; blue is the server's reply. The key line is the server's Content-Disposition header, which names the downloaded file.

Primary indicator: an invoice-themed ZIP delivered over plain HTTP from a courier-lookalike domain (quote.checkfedexexp.example) — a classic malware lure. The body is a labelled safe placeholder because this is a teaching capture. Click Close.

4Decoy fetch and C2 beacon

In the Wireshark GUI: clear the display-filter bar (top of the window), type the filter below, press Enter.

▼ filter http.request
Shows every HTTP request in the capture.

Look for the decoy GET /update/pas.txt and the same GET /1517096937 repeated five times to 203.0.113.45 — repeated identical requests to one host are command-and-control beaconing.

5DNS noise (domain generation)

In the Wireshark GUI: clear the filter bar, type the filter below, press Enter.

▼ filter dns.flags.rcode == 3
Shows only failed DNS lookups (NXDOMAIN).

A burst of failed lookups to random-looking names under dyn-c2.example is consistent with a domain generation algorithm cycling through addresses to find a live controller.

6Recover and hash the payload

Confirm the filename is in the capture, then recover the payload, fingerprint it, and lock it down.

strings lab01_sample.pcapng | grep -i "invoice"# pull readable text from the capture and search it for 'invoice' (case-insensitive)
printf 'SAFE-TEACHING-PLACEHOLDER: this is not a real archive or payload. Lab 01 synthetic sample.' > Invoice_876597035_003.zip# write the safe placeholder payload into a file (> creates the file)
sha256sum Invoice_876597035_003.zip# compute the file's SHA-256 fingerprint
chmod 000 Invoice_876597035_003.zip# remove all permissions as a safety habit (000 = no read/write/execute)
Expected: f560cab03cd50d7829c4ee3710d8fedf3f4cb1dcef662fb9cbc618049e508f09
Best practice: identify a suspicious file by its hash and check that hash against a reputation service (e.g. VirusTotal) — never re-upload the file itself.

7Log analysis (the brute-force spike)

Count failed logins by source IP, then bucket the events by hour to expose the spike.

grep "Failed password" lab01_auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr | head# find failed logins, pull the source IP, count each, sort by most frequent, show the top
awk '{split($3,a,":"); print a[1]":00"}' lab01_auth.log | sort | uniq -c | sort -k2# take the hour from each timestamp, count events per hour, sort by hour to reveal the spike
Expected: top sources ~189 / ~183 / ~180, then two spike hours of ~298 and ~254 failed logins (about 60× the quiet baseline) — an automated SSH brute-force burst, invisible until you baseline by hour.

9.5 Top three priorities

  1. Router (R-01, score 25) — four-year-old firmware exposing cleartext HTTP admin reachable from staff Wi-Fi. If the gateway falls, every other control sits on an untrusted network. Replace first.
  2. Cloud backup MFA (R-02, score 25) — one shared password guards backups of all 14,000 patient records. Enabling MFA and individual accounts takes minutes — the fastest large risk reduction available.
  3. Phishing (R-03, score 20) — an email was already clicked last quarter, so it is a confirmed pattern, not a hypothesis. Mandatory training plus email filtering closes the most-used entry path.

Fix order is driven by exposure, not cost — two of the three take minutes and cost nothing.
