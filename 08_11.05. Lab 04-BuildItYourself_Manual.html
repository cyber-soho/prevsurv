Build Your Own Lab 4 Evidence

Preventive Surveillance in Cybersecurity · 420-D01-AB · Cohort CYB-01 · Lab 4 (Anomaly Triage)
From the Industry to the Classroom - Building the IT's Future, Today and Together!

0.Read this first - what you are about to do

Instead of downloading an evidence pack, you are going to make your own copy of the three Lab 4 evidence items, right on your lab virtual machine, by running a short script that is printed in full further down. A few minutes of copy-paste and you will have the same capture, the same eight "quarantined" files, and the same domain-controller log everyone else is working from.

Why do it this way? Two reasons. First, it sidesteps the file-transfer headaches some of you ran into. Second - and this is the part worth slowing down for - building the evidence yourself is genuinely how analysts learn. You read a packet trace better once you have seen how one is put together. Nothing in this exercise is downloaded from anyone; you create every byte locally.

Nobody is attacking you. Read this twice.

Every file you are about to create is fake and harmless. The "exfiltration" traffic is a stream of random bytes going nowhere. The "malware" files are plain text that says, in plain English, that it is a training decoy - there is no program inside them, nothing executes, nothing phones home. The "brute-force" log is a list of invented rows in a spreadsheet. The company in the scenario, Plateau Realty Inc., does not exist.

Your instructor is not hacking your machine, and this kit cannot be used to hack anyone else's. It is a teaching set, the cybersecurity equivalent of a crash-test dummy. The only thing that looks scary is the naming - a file called svchost.exe or invoice.pdf.exe is meant to look suspicious so you can practise spotting the trick. Open any of them in Notepad and you will see the joke for yourself.

One thing your antivirus might do (and why it is fine)

This particular set was built to leave your antivirus alone - there is deliberately no live sample and no test-virus string in it, so a normal scan should pass without a peep. If you have an unusually aggressive endpoint agent it might still raise an eyebrow at a text file wearing an .exe costume. That is a false positive, not a real detection, and the fix is a thirty-second folder exclusion covered in section 6. Build everything inside your isolated lab VM - never on the laptop you use for banking, email, or work.

1.Before you start

You need your Linux sensor VM (CYB01-SENSOR-01, Ubuntu 22.04) with Python 3 and pip. The capture builder uses Scapy; the file and log builders use two small libraries for a real Word document and a real JPEG. Install all three in one line:

sudo apt update
sudo apt install -y python3-pip
pip install --user scapy python-docx pillow

If pip install --user is blocked on your build of Ubuntu, add --break-system-packages to that line. Make a working folder and move into it - the script writes everything into a lab4_evidence/ subfolder beneath wherever you run it:

mkdir -p ~/cohort-cyb01/lab4 && cd ~/cohort-cyb01/lab4

The Event Viewer and PowerShell steps later on (sections 2c and 3) happen on your Windows analyst VM, CYB01-ANALYST-01. You can do the whole network and file part on Linux first and deal with Windows after.

2.Build everything in one go

2a. Save the builder

Copy the script below into a file called build_lab4_evidence.py in your working folder. It is long because it is honest - every packet and every row is laid out so you can read exactly what is being made. Nothing is hidden, and nothing in here is dangerous; it is all print, random bytes, and ordinary file writes.

build_lab4_evidence.py

2b. Run it

python3 build_lab4_evidence.py

You should see three lines confirming the capture, the eight decoy files, and the log. Take a quick look at what landed:

ls -la lab4_evidence lab4_evidence/suspicious_files
file lab4_evidence/suspicious_files/*

Notice that file calls invoice_apr_2026.pdf.exe and svchost.exe plain ASCII text, not programs. That mismatch between the name and the real content is the first thing a triage analyst writes down. Notice too that five of the decoys share the exact same modify time (22:07:30) - ordinary files are never all touched in the same second, and that cluster is your "these were dropped together" signal.

A note on Linux timestamps

If you run stat after you have already opened a file, the access time will read as "now" - that is just Linux updating it as you look. Lean on the shared modify time across the five decoys for the dropper pattern on Linux, and on the Born-time cluster you will set on Windows in section 3.

2c. (Windows only) make the log openable in Event Viewer

The Python step gives you the log as a CSV and a JSON, which is enough to start. To do the Event Viewer half of Lane 3, copy your lab4_evidence folder to the Windows analyst VM, then run this once in an elevated Windows PowerShell 5.1 window from the folder that holds it. It stages the rows in a throwaway log and exports a real dc01_security.evtx:

make_evtx.ps1

3.(Windows only) put the file timestamps back

Copying files onto a Windows share resets their creation time to the moment they arrived, which quietly erases the timeline you just built. Run this small script from the folder holding lab4_evidence to restore it - five decoys stamped as if dropped together at 22:07:30, three ordinary files with believable, spread-out histories:

set_timestamps.ps1

Now L2_file_triage.ps1 will show Born = Modified = Accessed all bunched at 22:07:30 on the five decoys - the textbook dropper signature - while the three controls look like normal documents from earlier in the year.

4.The VirusTotal step - what does "malicious" actually look like?

Lane 2 asks you to look a file's hash up on VirusTotal and read the verdict. Here is the honest situation: none of your eight decoys is malicious, so every hash you submit from them will come back clean. That is a real result and worth writing down - "quarantined" never means "confirmed bad", and a good chunk of triage is clearing files, not condemning them.

But you should also see what a genuine detection looks like, without ever putting a real sample on your machine. The safe, industry-standard way to do that is to look up a hash - a 64-character fingerprint is just text and cannot run anything. Use the fingerprint of the well-known antivirus test file (the EICAR test file - read about it at eicar.org). Paste this into the search box at virustotal.com/gui/home/search:

275a021bbfb6489e54d471899f7db9d1663fc695ec2fe2a2c4538aabf651fd0f

You will see roughly sixty engines flag it, with a tidy verdict like EICAR-Test-File. Screenshot that for your report as your example of a malicious verdict, and contrast it with the clean result from one of your own files. You never downloaded or created the sample - you only asked a database a question, which is exactly the habit this lab is trying to build. Always look up the hash; never upload the file.

5.If your antivirus gets nervous

This kit is built to slip past a normal scan, so most of you will see nothing. If your endpoint agent is the jumpy sort and quarantines a decoy anyway, do not panic and do not assume something is wrong - it is reacting to a name or a shape, not to real code. Add a folder exclusion for your lab directory and carry on.

Microsoft Defender: Windows Security → Virus & threat protection → Manage settings → Add or remove exclusions → Add an exclusion → Folder → pick your lab4_evidence\suspicious_files folder. Or, from an elevated PowerShell:

Add-MpPreference -ExclusionPath "$HOME\cohort-cyb01\lab4\lab4_evidence\suspicious_files"

If a file already got pulled into quarantine, restore it from Windows Security → Protection history. On Linux, ClamAV and friends will not touch these at all. If anything ever genuinely worries you, stop and message the instructor before going further - that instinct is the right one to keep.

What this material is

This is an authorised teaching supplement for cohort CYB-01 of course 420-D01-AB.
